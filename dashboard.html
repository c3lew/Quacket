等你決定:「更新不用重開程式」和「快捷鍵跳到挑 issue 那區」這兩個你提過的想法 — 要現在插隊做,還是等目前這條線(還有兩個功能)做完?我的建議是等做完,這條線每一格都在補「報告不會弄丟、不會變兩篇」,中間插隊會讓半成品多待幾天。
那三個小毛病是什麼(都是你看過、拍板「之後修」的):
1. 送出卡到一半沒下文的時候,程式在硬碟上把它記成「失敗」,實際處理卻當成「還不確定」在走 — 行為是對的,兩個字不一致而已,只有以後查問題的人會被誤導。
2. 萬一同時卡了兩份沒確認完的報告,那兩列長得一模一樣,分不出誰是誰 — 按鈕本身是對的(按 A 不會動到 B,拿真的 GitHub 驗過),只是「你按的是哪一份」不夠明顯。要連續中斷兩次才遇得到。
3. 網路整個斷掉的時候,錯誤訊息會寫成「不確定你用哪個 GitHub 帳號登入」— 講的方向錯了,實際是沒網路。訊息誤導,不影響資料。

最近幫你做的決定

  • 8/16驗收清單原本寫「每一種狀況都要給你一個下一步」,你看過實際畫面後改掉了這行字:結果還在查的時候不給按鈕才是對的 — 那顆按鈕不是按了沒反應,就是重複再問一次。改的是規格的措辭,不是程式。
  • 8/16同一列裡一半寫「還在確認」、一半寫「送不出去」,自相矛盾 — 你當場判「現在修」,改成從頭到尾都講「我們還不能確認」。這片主打把話講清楚,留一句打架的話等於砸自己招牌。
  • 8/16「按下再確認之後,按鈕會消失、不會被連按兩次」這件事,原本的自動檢查講不出來(它驗的是測試自己寫的複製品,不是真的程式)。補了一條把查詢停在半空中的檢查,現在真的釘住了。
  • 8/16重開後的自動確認,會先等幾秒再去問 GitHub — 因為剛送出去的東西,GitHub 那邊要幾秒才查得到,問太快會得到「沒有」而害你被送兩份。代價:自動確認從一瞬間變成最多等 18 秒,但這個等待完全在背景,你照樣能打字。
  • 8/16那個「查太快會送兩份」是實測抓到的,不是猜的 — 用真的 GitHub 量了兩輪,剛開好的報告要 4.3 秒和 6.9 秒才查得到。修完重測三次都只送一份。
  • 8/16有一條自動檢查是直接改硬碟上的紀錄來製造情況,不是從畫面操作出來的 — 因為那個情況從畫面根本做不出來。代價:以後存檔格式改了,這條檢查要跟著改。
  • 8/15「畫完標註再送」這條不補自動檢查,改由你換裝新版後親手驗一次(已驗過,新內容有帶到)— 比補一套測試快,也更接近你真的會怎麼用。
  • 8/15自動檢查沿用現有工具,不多裝一套真瀏覽器測試 — 一個指令幾秒跑完;代價是測的是模擬視窗,不是真的程式視窗。要換隨時換得掉。
